# MinIO operations — local development cutover verified

**Status: local development Compose and Next app use MinIO for product images; production deployment remains unapproved.** The source-built server and source-built `mc` are local images, not authenticated/published production digests. The checked-in Compose service has no default image and refuses to render without `MINIO_IMAGE`. On this development host, ignored `.env` now sets `PRODUCT_IMAGE_STORAGE_DRIVER=minio` using scoped app credentials; logo/favicon remain local. Four referenced product images were copied to the private bucket without deleting local originals. This is a local-development single-node layout, **not** a production HA deployment.

The same provenance, digest, and test requirement applies to a separately approved `mc` executable. Reassess patch support and AGPL obligations with maintainers before production use; an archived source commit cannot promise future security fixes. Never substitute AIStor or an arbitrary third-party image as though it were this upstream release.

## Local setup (production only after the unblock gate)

1. Copy `.env.example` to untracked `.env`; provide verified `MINIO_IMAGE`, distinct strong `MINIO_ROOT_USER` and `MINIO_ROOT_PASSWORD`. Set `S3_REGION=us-east-1`, `S3_BUCKET=besties-media`, and `S3_ENDPOINT=http://127.0.0.1:9000` when Next.js runs on host; use `http://minio:9000` if the app runs on the Compose network. `S3_FORCE_PATH_STYLE=true`. Set `PRODUCT_IMAGE_STORAGE_DRIVER=local` until migration is verified. Reserve 9000/9001 locally, ensure Docker has sufficient free disk, and backup PostgreSQL and local image root **before any actual migration**.
2. `docker compose config` validates interpolation (all services require the image variable to render); `docker compose up -d minio` starts only MinIO. `docker compose ps minio` and `docker compose logs minio` show readiness. Do not use `docker compose down -v` or delete `minio_data`; a named volume is persistent but **not a backup**. Console/API bind only to `127.0.0.1` on Docker host, not to the public website. For access across hosts, configure trusted TLS/CA and network restrictions; never disable TLS verification.
3. Install a separately verified MinIO `mc` client (tag/digest/architecture recorded offline). Execute `docker/minio/bootstrap.sh` explicitly from a POSIX shell with `MC=/absolute/path/to/mc`, `MINIO_URL=http://127.0.0.1:9000`, root credentials, `S3_ACCESS_KEY_ID`/`S3_SECRET_ACCESS_KEY`, and **separate** `S3_MIGRATION_ACCESS_KEY_ID`/`S3_MIGRATION_SECRET_ACCESS_KEY` in process environment or a protected secret manager. Do not put secrets on CLI or in committed files; restrict terminal logs and environment access. Provision only on isolated dedicated instance: script refuses buckets other than `besties-media`; never change an existing bucket's anonymous policy automatically. Reruns stop if any IAM user/policy already exists (even after a partial run); inspect all existing grants and finish provisioning manually instead of overwriting identities or silently widening access. Existing secrets are not overwritten or rotated. The script is not a startup sidecar.
4. `docker/minio/app-policy.json` grants Get/Put/Delete object on `besties-media/*`, no ListBucket, admin, or other buckets. `docker/minio/migration-policy.json` grants ListBucket and Get/Put on this bucket only, no Delete. Policies are **static**; using a different bucket requires auditing both JSONs and the script, not merely changing env. Verify the bucket remains anonymous `none` (`mc anonymous get ALIAS/besties-media`), that app credentials can put/head/get/delete a disposable test object but cannot list this bucket or access a different bucket, and that anonymous reads fail. Use a unique test key and retain it through the restart check. Test migration credentials independently; never give migration/root secrets to the app.
5. Restart MinIO (`docker compose restart minio`) and verify the test object's persistence **before deleting only that known test key**, verify health after restart, and complete migration/cutover checks in [migration plan](minio-migration-plan.md). App-side product image facade, API integration and cleanup queue are implemented separately; app-route and IAM MinIO modes remain untested until this gate passes.

## Full-volume local restore drill (operator-gated; executed once under local maintenance)

`docker/minio/minio-volume-restore-drill.ps1` has a default **dry-run preflight** (`& ./docker/minio/minio-volume-restore-drill.ps1`): it checks the exact healthy Compose container and `webkygui_minio_data` mount, but does not mount/read the volume or create Docker resources. A local preflight passed; under the later authorized maintenance window, a full-volume snapshot and isolated restore also passed (see evidence above). Do not treat that on-host test as an off-host disaster-recovery backup.

To run after explicit maintenance authorization, freeze **all MinIO writers** (application uploads/deletes, migration, cleanup, administrative console, other clients) for the full snapshot window without stopping the live MinIO service. Independently confirm the correct deployment, healthy service, source volume, sufficient disk, Docker runtime and source-built image, four verified immutable manifest entries in ignored `.private/minio-local-apply-manifest.json`, and ignored root/app/migration credential files. Then run `& ./docker/minio/minio-volume-restore-drill.ps1 -ConfirmedNoMinioWrites`. The switch is an **operator attestation**, not a technical write lock; do not use it if any writes might overlap. The script never invokes Compose up/down/restart, attaches the source volume **read-only** to a networkless Alpine snapshot container, retains a tar and SHA-256 under ignored `.private/minio-volume-drill-<id>/`, restores that entire tar to a **new** volume on an internal Docker network, and runs a restored MinIO container from the inspected local image ID with **no host ports**. A disposable Node client verifies four GetObject byte SHA-256 values and lengths against the manifest, separate app/migration privileges (including denied actions), and anonymous bucket/object denial. Probe writes/deletes operate on restored storage only. The disposable container, volume and network are removed; the private archive/report remain for review. Never publish the snapshot: it contains MinIO IAM credentials and all objects; restrict access, encrypt and copy to independent retained storage per policy. No secret values should appear in report/stdout.

Limitations: the online tar is consistent only if operators truly quiesce writers; the script cannot enforce a distributed write freeze or prove the original manifest reflects a current DB transaction. Confirm fresh DB `ItemImage` inventory and backup PostgreSQL plus local logo/favicon root at a coordinated point before production claims. This local on-host archive is not off-host/versioned disaster recovery; restoring to the same machine does not test host loss. Current local images and IAM are not production-approved. The script tests a single-node filesystem layout, not multi-node erasure coding, concurrent mutations, or actual application cutover. The migration/cleanup probe only deletes disposable keys; it never deletes live objects.

## Maintenance and incident handling

Monitor readiness, errors, available volume capacity, backup freshness, and cleanup backlog; alert before disk fills. If full, stop new product-image writes, add capacity and recover from verified backup; never remove unknown objects to reclaim space. Back up the **MinIO object data, PostgreSQL metadata and local logo/favicon root** together to independent storage with versioned retention; a mirror that propagates deletes or a named volume alone is not a backup. Restore to an isolated fresh environment and compare the live `ItemImage.storageKey` manifest (size and SHA-256 of object bytes), as well as local logos; do not treat ETag as a SHA-256 checksum.

For root/app/migration credential rotation, plan a maintenance window, create new separately scoped identity, verify least-privilege operations, update server-only app secret and restart/retest, then disable old identity after confirming no clients use it; avoid overwriting existing credentials in bootstrap. Upgrade only via the same reviewed source/build/digest process, with full restorable backup and isolated compatibility/restart/restore test; pin the new digest explicitly. No automatic floating-tag upgrade. If MinIO is unavailable, keep logo/favicon local operational and never silently fall back product images to local. Before any rollback after MinIO writes begin, follow the plan's DB/manifest/checksum reconciliation; never just flip the driver.
